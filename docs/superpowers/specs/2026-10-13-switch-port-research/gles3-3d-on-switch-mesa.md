# Godot 4.7.2 Compatibility (drivers/gles3) on Switch homebrew via devkitPro switch-mesa 20.1 — what works, breaks, needs workarounds

Researched 2026-10-13. Repo: `/home/aisuko/gamedev/godot-nx` @ `0c76a51e10` (branch `switch-4.7`, `version.py` = 4.7.2-stable), read-only. Builds on the two prior wayfinder notes (`git show HEAD:.scratch/switch-port/research/05-gpu-stack.md` and `.../03-prior-art.md`); facts restated from them are marked [prior-05]/[prior-03] and were re-verified against the sources below where it mattered. Downloaded sources are in `scratchpad/dl/` (Ozuba files at HEAD and at the first/pre-Vulkan commits, the devkitPro mesa patch, mesa 20.1.0 `features.txt`/`extensions_table.h`/`nvc0_screen.c`/`st_cb_texture.c`/`nouveau_screen.c`, Stary's `rasterizer_storage_gles3.cpp` and issue list).

## Summary

1. **Nobody has demonstrated Godot 4.x Compatibility on portlib `switch-mesa` 20.1.0-rc3.** Ozuba's first three days of commits (2026-06-09..11) *did* target it (`LIBS = EGL GLESv2 glapi drm_nouveau`, ES 3 context, `make_current(false)`), the README of that era says only "First compilable implementation" and that ETC2 "is decompressed in software by Mesa"; on 2026-06-12 the GLES3-over-portlibs path was declared "deprecated ... scheduled for removal" and all later work runs GLES3 through zink/NVK or Mesa-26 nvc0 from the community "unified Mesa Horizon SDK". No commit message or README states that portlib GLES3 rendered anything on hardware, nor that it failed. Treat it as *unproven*, not *disproven* [O1][O2][O3][O4].
2. **Everything the 3D path needs at the API level is present in mesa 20.1 nvc0 in both context flavours** (GL 4.3 core / GLSL 4.50, or ES 3.1 / ESSL 3.10): UBOs, texture arrays + `glFramebufferTextureLayer`, instancing, transform feedback (particles/skinning), `glBlitFramebuffer`, `glMapBufferRange`, fence syncs, MSAA renderbuffers up to 8×, `GL_RGB10_A2` cubemaps with mips, `samplerCubeShadow`, `gl_FragDepth`, `GL_DEPTH24_STENCIL8`, float colour buffers, norm16, anisotropic filtering, KHR_debug, S3TC/RGTC/BPTC natively — **in ES contexts too** (mesa exposes `EXT_texture_compression_s3tc/rgtc/bptc`, `EXT_texture_norm16`, `EXT_color_buffer_float`, `OES_texture_float_linear`, `EXT_sRGB_write_control`, `KHR_debug` to ES) [M1][M2][M3].
3. **Three things are genuinely missing/broken on this stack**: (a) no program-binary formats → Godot's shader cache is a no-op, every boot recompiles every variant on a single thread through the TGSI path; (b) no ASTC and no native ETC2 (chipset gate `0x12b`/`NVEA` vs reported `0x120`) → ETC2 textures are CPU-decoded to RGBA8 by mesa (8× memory, slow uploads) and ASTC is CPU-decoded by Godot; (c) `eglQuerySurface(EGL_WIDTH/HEIGHT)` returns 0 (open devkitPro/mesa #1) [M4][M5][M6][M7][D1].
4. **Pick ES mode (`make_current(false)`, `EGL_CONTEXT_CLIENT_VERSION 3`, `-lGLESv2`, no GLAD)** — it is what Stary (3.x) shipped and what Ozuba wrote; it avoids GLAD's `dlfcn.h` dependency, the `EGLManager`/`EGL_STATIC` assumptions, GL-mode timer queries (which hit the one `#if 0 // TODO: Support queries` hunk in the patch), `glGetTexImage`, and leaves only one Godot-side wrinkle: 4.7.2 hard-codes `etc2_supported = true` in ES mode, so Switch exports must be S3TC/BPTC (platform features `s3tc`,`bptc`) and ETC2 must never reach the device [G1][G2][G3][M8].
5. **720p30 3D is plausible but unmeasured.** The only data points are 2018-era ports on the same stack: ioquake3 at a steady 60 fps/720p, Doom 3 (dhewm3) at 20–30 fps/720p shadows-off on a driver "still in early stages", and OpenMW 0.46 (GL 2.1) "performance isn't very good"/CPU-bound. GPU runs at 307 MHz handheld / 768 MHz docked; homebrew can raise it (dhewm3's `nx_overclock`). Godot's Compat 3D is heavier per pixel than Quake 3 and lighter than OpenMW's scene load; expect it to land between those, and plan for `mobile`-class project settings (2048 directional shadow, hard shadows, no SSAO/glow) [P1][P2][P3][P4].

## 2. Inferences (not measured on hardware)

1. **ES-mode `Config` outcome on nouveau ES 3.1** (from [M1][M2][M5][G1]): `float_texture_supported = true`, `float_texture_linear_supported = true`, `etc2_supported = true` (hard-coded), `s3tc_supported = true` (`GL_EXT_texture_compression_s3tc` is in the ES string), `rgtc_supported = true`, `bptc_supported = true` (`GL_EXT_texture_compression_bptc`), `astc_* = false`, `srgb_framebuffer_supported = true`, `unorm16_texture_supported = true`, `support_anisotropic_filter = true` (value from the GM20B max, 16), `msaa_max_samples = 8`, `msaa_supported = true`, `multiview_supported = false`, `msaa_multiview_supported = false`, `rt_msaa_* = false`, `external_texture_supported = false`, `use_depth_prepass = true` (renderer "NV120" matches none of "PowerVR,Mali,Adreno,Apple"), `polyfill_half2float = true` (harmless GLSL polyfill), no Adreno/PowerVR quirk paths. `GL_MAX_UNIFORM_BLOCK_SIZE` on nvc0 is 64 KiB → within Godot's clamp.
2. **GL-mode outcome (GL 4.3 core)** would also work (`etc2_supported = false` → Godot decompresses ETC2 itself), but costs: GLAD must be compiled with a `dlfcn.h` shim, `EGL_STATIC` assumptions in `EGLManager` must be bypassed anyway, `glQueryCounter(GL_TIMESTAMP)` runs every frame through the patch's untested query setup, `glGetTexImage` is used for `texture_2d_get`. Net: no feature gained for 3D (both modes get the same formats), more untested surface. ES mode it is.
3. **ETC2 on the device is the single biggest hidden cost**: with `etc2_supported = true` Godot uploads ETC2/EAC blocks, and mesa transcodes them on the CPU every upload (`_mesa_unpack_etc2_format`) into RGBA8/R16 — 4–8× texture memory out of the shared process heap, plus A57 CPU time proportional to texel count at load. Stary's 3.x games lived with this (all textures ETC2) — proof it *works*, not that it is cheap. For 4.7 the export preset must advertise `s3tc`+`bptc` and `rendering/textures/vram_compression/import_s3tc_bptc` must be on; a platform feature list of `etc2`/`astc` must *not* be used. Belt-and-braces: a one-line `#ifdef HORIZON_ENABLED etc2_supported = false;` in `config.cpp` makes Godot decompress on its side (same CPU cost, but it is then visible in Godot's profiler and uses Godot's own decoder) — optional.
4. **Shader compile time will dominate first-frame/first-material hitches**: no program binaries (so Godot's `shader_cache` directory is written but useless), no glthread, no mesa threads (`HAVE_PTHREAD` undefined → single compile thread), 2020-era TGSI → nv50_ir on an A57 at 1 GHz. Godot 4.7's `scene.glsl` specialisation variants are compiled lazily per material/light configuration. Mitigation options in order of effort: (i) project-side warm-up scene that touches every material; (ii) ship Godot's `.cache` files anyway (they help nothing here); (iii) extend `ShaderGLES3` with a Switch-only "precompile all specialisations used in the last run" list persisted under `user://` — compile order only, still full cost; (iv) long-term: the Mesa 26 nvc0 port has a disk cache (Ozuba sets `MESA_SHADER_CACHE_DIR`) but its GL path is reported black-screen [M10].
5. **Timer queries**: `PIPE_CAP_QUERY_TIMESTAMP` is advertised and the `#if 0` only removes the `NVIF_CLASS_SW_GF100` software object whose only upstream use in 20.1 is the `SUBC_SW` bind at init; so `glGenQueries` (always called) is expected to succeed and ES mode never issues `glQueryCounter`. Risk is low but *verify* `glGenQueries` + `EXT_disjoint_timer_query` do not error on first boot.
6. **MSAA**: Godot's non-Android path uses `glRenderbufferStorageMultisample` + `glBlitFramebuffer` resolve (full bandwidth cost on a 25.6 GB/s LPDDR4 part); nvc0 allows 2/4/8. 2× or none at 720p is the realistic setting; 4× docked at 1080p is likely too expensive.
7. **Applet-mode memory**: GPU buffers and textures come from the process heap. hbmenu-applet launches have a small heap and every 3D port OOMs there; Godot 4.7 itself (Jolt, ~200 MB of engine allocations) plus GPU buffers means **title takeover (or NSP forwarder) is effectively mandatory for 3D**; Stary's splash-and-exit guard for `appletGetAppletType() != Application` [prior-03] is the right UX.
8. **`discard` crash (Stary #28)** is unresolved and the repro is a 3.x canvas shader; Godot 4.7's `scene.glsl` uses `discard` for alpha-scissor and depth-prepass alpha, so this must be among the first hardware tests. Plausible cause is a nv50_ir TGSI `KILL` corner case in the GM107 emitter; if it reproduces, the workaround is `ALPHA_SCISSOR` → blend/`alpha hash` and avoiding `discard` in user shaders.
9. **Performance envelope for 720p30**: Doom 3's per-pixel lit, stencil-shadowed scenes at 20–30 fps on the *2018* driver, Quake 3 at 60, OpenMW CPU-bound — Godot Compat 3D with a depth prepass, ≤8 lights/object, one directional shadow (2048, hard), no glow/SSAO, S3TC textures, 2× MSAA or none, and the Jolt/scene-tree CPU side on three A57 cores (Godot's `get_processor_count()` = 3 in Ozuba) should reach 30 fps for small-to-medium scenes in handheld mode; docked 1080p will need `scaling_3d` (bilinear, e.g. 0.67). The CPU side (GDScript, physics) is as likely to be the limiter as the GPU, as OpenMW showed. Raising clocks via `clkrst`/`pcv` from inside the app (as dhewm3 does) is an option worth exposing as a project setting.
10. **Docked/handheld switch**: `nwindowSetDimensions` must precede surface creation and the EGL surface must be recreated on `AppletHookType_OnOperationMode` (Ozuba does this); Godot then needs `window_resize` → `RenderSceneBuffersGLES3::configure` (automatic via the rect-changed callback). Because `eglQuerySurface` returns 0, the size must come from the applet mode or `nwindowGetDimensions`, never from EGL.

## 5. Minimal GL manager a Switch platform needs (shape)

- `platform/switch/platform_gl.h`: `#define GLES_API_ENABLED`, `#include <GLES3/gl32.h>`, `<GLES3/gl3ext.h>`. `platform_egl.h`: `<EGL/egl.h>`, `<EGL/eglext.h>` (compile with `-D__SWITCH__` so `eglplatform.h` picks `void*` native types [prior-05 S3]).
- `detect.py`: `opengl3=True`, defines `GLES3_ENABLED HORIZON_ENABLED __SWITCH__ ...`; libs `EGL GLESv2 glapi drm_nouveau nx m` in that order (static archives, single pass); glad is never compiled for a `switch` platform: `drivers/gl_context/SCsub` only adds `thirdparty/glad/gl.c` and defines `GLAD_ENABLED` (plus `EGL_ENABLED GLAD_GLES2` on linuxbsd/angle) when `env["platform"] in ["macos", "windows", "linuxbsd"]`, so `GLAD_ENABLED`/`EGL_ENABLED` stay undefined and `RasterizerGLES3` takes the Android-style no-loader path. Add `HORIZON_ENABLED` to the two `EGL_ENABLED || ANDROID_ENABLED` guards in `rasterizer_gles3.cpp` if the ES `glDebugMessageCallback` lookup is wanted (Ozuba did).
- One class (`GLManagerSwitch` or inline in `DisplayServerSwitch`), ~120 lines, exactly Ozuba's `_initialize_egl/_finalize_egl` plus `make_current`, `release_current`, `swap_buffers`, `set_use_vsync` (→ `eglSwapInterval`), `get_window_size` (from applet mode / `nwindowGetDimensions`), `resize` (destroy surface → `nwindowSetDimensions` → recreate surface → `eglMakeCurrent`). Register the display server with `opengl3` as the only driver and call `RasterizerGLES3::make_current(false)` after the context is current.
- Optional env before `eglInitialize` (mesa reads `getenv`): `MESA_NO_ERROR=1` for release, `EGL_LOG_LEVEL=debug`/`MESA_VERBOSE=all`/`NOUVEAU_MESA_DEBUG=1`/`NV50_PROG_DEBUG=1` for debugging [prior-05 S5]; `MESA_GLES_VERSION_OVERRIDE` is honoured if an explicit 3.0 context is wanted for A/B testing.
- Core-profile alternative (not recommended): `eglBindAPI(EGL_OPENGL_API)`, `EGL_CONTEXT_OPENGL_PROFILE_MASK_KHR = CORE`, major/minor ≥ 3.2 (the driver falls back to compatibility profile below 3.2, which caps GLSL at 1.30 [M4][prior-05 S8]), `make_current(true)`, GLAD compiled with a `dlfcn.h` stub.
